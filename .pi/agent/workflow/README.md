# Personal Pi workflow

**Plan → per-feature Build ↔ Review → whole-plan Review ↔ focused Build → optional UI → Finalize.** Guidance, not a permission system.

Installed through `~/.pi/agent/extensions/workflow-modes.ts`. Reload/restart Pi after changes. Ordinary Pi stays untouched until a phase is selected. Pi owns the model, thinking level, tools, permissions, and project trust; there are no workflow profiles.

## Commands

| Command | Job |
| --- | --- |
| `/plan [task or report]` | Create/reuse a Git task branch/worktree, or work in place outside Git; investigate, save a standalone plan, and ask for approval. |
| `/build [plan]` | Read the plan/progress, implement the selected eligible feature (or focused whole-plan corrections), run relevant checks, then hand off to independent Review. |
| `/review [plan/reference]` | Independently inspect changes/checks and save a standalone findings or no-findings report. |
| `/ui [plan/reference]` | Optional human visual review, with an inspected Pi-owned dev server or a supplied user-managed URL. |
| `/finalize [plan/reference]` | Consolidate this task's final decisions at its plan path, remove consolidated artifacts, update instructed journals/logs, then return without publication outside Git; in Git, with task/publication authority, make a signed task commit, push over existing SSH, create/reuse a gh PR, report its URL and return. |
| `/workflow-exit` | Return to the original launch cwd in fresh ordinary Pi, without publication or task cleanup. |
| `/workflow` | Show phase/input, validated task identity, artifact defaults, review target, and recovery/help. |

Each phase command starts a **fresh independent session** in the managed Git task worktree or the actual non-Git directory. Outside Git, any phase may start directly. Repeating or switching phases also starts fresh. In Git, direct Build/Review/UI/Finalize outside a managed task pauses: enter the correct worktree first, or start `/plan` for a new task. Existing unassociated tasks need explicit recovery direction, not automatic migration. No `/new` requirement, mandatory phase order, approval records, or completed-session lock. Commands begin immediately; missing inputs are clarified in chat. Plan input is interpreted by the agent, not a filename-suffix parser. The command's entire argument is text, not shell syntax; spaces, quotes, backslashes, and multiline tasks are not shell-expanded or executed.

Phase and input follow the active session branch and restore on reload/resume/tree navigation, without automatically running work. Old `workflow-state` entries/approval receipts are ignored, not migrated or deleted; start the desired phase again for an old session.

## Non-Git tasks: in place

In a genuinely non-repository directory, all five phase commands work directly on its actual files. No repository/worktree, copying, directory metadata, snapshot or backup is created. **There is no isolation, Git baseline or implicit rollback**, including for symlink destinations. Git checkouts/subdirectories retain the managed behavior below; unborn repositories, broken metadata, missing Git, process/permission errors and aborted discovery never authorize fallback.

Non-Git identity is tagged separately and lives only in the existing branch-sensitive session entry: a UUID, canonical root/original cwd, and project key derived from the directory name plus a hash of its canonical path. No fake repository, branch or commit. Handoffs/replanning and reload/resume/tree restoration retain identity, exact inputs and notes; restoration starts no work. Resume the Pi session to continue the same task. A new unrelated session starts a distinct task, even in the same folder; there is no directory registry, latest-task discovery or identity recovered from plan filenames. An explicitly supplied old plan/report keeps its exact path and any per-artifact override.

Artifacts still default to the usual home plans/reviews folders grouped by project/task. Review reads explicitly scoped task files against the plan and check evidence, asks if scope is unclear, and discloses the missing baseline rather than claiming exhaustive diff detection. Clean standalone/whole-plan Review offers only **Approve code and go to UI** or **Approve code, skip UI, and go to Finalize**. No browser file review or replacement config annotation outside Git; chat feedback/approval and optional live UI remain available. The UI helper accepts inspected app directories within the canonical root and rejects escapes, including symlinks; ownership/cleanup rules are unchanged.

Successful non-Git Finalize performs the same bounded consolidation, instructed bookkeeping and scoped documentation verification, reports outcomes, then automatically calls `workflow_exit` without `publicationUrl`. Incomplete/failed consolidation, bookkeeping, cleanup or checks stays for recovery. No commit, push, PR, signing or authentication work. Publication URL context is rejected by both helper and internal command. A repository appearing later pauses this task for direction, never grants Git publication authority.

Explicit `/workflow-exit` or `workflow_exit` returns to fresh ordinary Pi in the original directory, starts no work, disables phase tools/guidance and preserves files/artifacts. It performs no Git status and claims neither clean nor dirty state. Identity is not rediscovered after return: resume the retained session for continuation. Cancellation/failure reports actual-cwd/manual recovery; selected model/thinking, host exclusions and custom session directory follow ordinary Pi replacement behavior.

The worktree, diff-review and publication instructions below apply only to managed Git tasks; common loop, artifact, UI and consolidation safeguards apply to both kinds.

## Managed Git task workspace lifecycle

Only `/plan` from an unmanaged Git checkout creates a task: one unique `pi/<UUID>` branch and worktree under `~/.pi/worktrees/<project-key>/<UUID>/`, starting at the launching checkout's exact committed HEAD. Pi displays the source branch/commit, preserves the launch subdirectory when committed, and actually replaces its session cwd so instructions, trust, extensions, and built-in tools reload for that workspace. Source files, index, and checked-out branch stay untouched. Worktree creation changes shared Git refs/administration; it is the narrow setup exception to Git-read-only guidance, not general agent Git-write authority.

Staged, unstaged, or untracked source changes require **Proceed from committed files only** or **Cancel**. Nothing is copied, stashed, staged, or transferred. Escape/abort chooses nothing. Without UI, dirty-source creation pauses with interactive/RPC recovery instructions. Missing Git/HEAD, missing committed subdirectories, invalid association, and switching failures pause without running the phase in the source checkout. Partial setup retains and reports its branch/worktree/session paths; no destructive rollback or automatic adoption of existing resources.

Replanning and every numbered feature/phase reuse the same task checkout. A fresh Pi there can enter a phase and see pending files without inheriting conversation history; resume/tree restoration never dispatches work. Start another task by launching `/plan` from the original checkout. Minimal task association lives in the worktree's Git administrative directory (`workflow-task.json`), not tracked files or a progress/approval store, and travels in branch-sensitive phase state. Repository and branch mismatches pause for recovery.

Initial cross-cwd entry serializes a header, setup entries, and a visible workflow workspace notice from the public SessionManager JSONL contract, then uses Pi's supported `switchSession` and fresh callback context. The notice lets Pi restore selected model/thinking without copying source history or inventing assistant messages. It preserves the existing session storage directory (including a custom one), selected model/thinking, literal inputs, and host tool exclusions; if the selection cannot be restored, phase dispatch pauses. Replacement failures report the original error and retained paths through the captured UI notification channel, without relying on an invalidated context; relaunch Pi in the retained task workspace if replacement failed. Ephemeral runs pause before creation because safe supported cross-cwd entry requires a persisted session. Later phases use ordinary `newSession`.

Worktrees isolate checkout files, **not permissions, shared services, ports, credentials, or symlink destinations**. Ignored dependencies/secrets and submodules are not provisioned. No fetch/pull, integration, branch/worktree deletion, production activation, signing, or publication is performed by workspace setup. UI alone may start/stop an inspected existing dev command through `workflow_ui_server`. Authorized Finalize uses ordinary Git/gh tools for task-only publication as described below. After extension setup, Plan remains non-mutating; Build/Review remain Git-read-only except explicitly authorized disposable test fixtures. Finalize's publication exception requires established task authority and human code/UI approval or a direct publication instruction; a documentation-only Finalize or standalone Review does not grant it. Setup grants no general Git, service, credential, destructive, installation, or deployment authority.

## Requested return to ordinary Pi

Use `/workflow-exit` or explicitly ask in chat to return without publishing; the agent calls **`workflow_exit`** with no arguments and ends its turn. Chat intent is interpreted normally, not by a global phrase interceptor. The helper defers to the command-only replacement path after its tool returns. The command also works in a fresh Pi inside a managed task, with no selected phase.

Return validates the recorded source repository/directory and opens a **new ordinary session** at the exact original launch cwd, including its subdirectory. It does not resume an old source conversation. The badge is auto, workflow helpers/guidance are inactive, and the visible return notice starts no model turn. It does not change the parent shell's directory, either checkout's Git state, or any task files, sessions, descriptors, artifacts, branches, or worktrees. Pending task files are disclosed and left behind, not a blocker; exit is not completion, approval, integration, or publication.

Cancellation, missing/mismatched source, or replacement failure preserves retained resources and reports recovery paths; verify actual cwd before continuing, especially if replacement already invalidated the old runtime. Relaunch Pi manually in the original directory for ordinary mode, or enter the retained task checkout and select a phase/resume its session. A later `/plan` from the original unmanaged checkout creates another task. Exit itself never publishes, including after a statement about finishing a manual commit. Return stops any Pi-owned UI server before replacing the session. After verified authorized publication, Finalize reports the actual PR URL and calls `workflow_exit` with optional `publicationUrl` display context. The fresh ordinary-session notice retains that URL; it is not a publication receipt, validator or authorization. No arguments always means return without publishing.

## Feature identities and progress context

Keep one original implementation plan with numbered features, stable identifiers, per-feature acceptance criteria, ordered steps, and explicit dependencies where needed—not a feature per file/test or separately approved feature plans. Single-feature and older unnumbered plans remain one implementation unit unless divisions/dependencies are genuinely ambiguous.

Every implementation Build/Review session reads the complete original plan, applicable instructions, and latest same-task progress/review references. Existing handoff `notes` carry explicit loop authorization, current feature identity or whole-plan review kind, next action, and absolute latest/predecessor/clarification report paths. A filename or prior report does not establish loop authority. Keep the original plan primary and unchanged during implementation; preserve earlier reports until Finalize's bounded consolidation.

Reuse Review reports as cumulative progress snapshots: all feature states, dependencies/blockers, stable finding IDs and status/evidence, actual checks, and next eligible work, with original-plan and predecessor references. If a blocker prevents Build's normal Review handoff, save a focused standalone blocker/progress report under the review-report path rules instead of a routine build journal or separate state store. Partial work is not complete or reviewed. Reconcile missing, stale, or conflicting progress from code, checks, and reports before continuing; restoration never automatically dispatches work. These are prompt contracts, not a progress parser or scheduler. Plan approval can authorize the per-feature implementation/review loop and in-scope corrections, not new scope/design, dependencies, installs, destructive operations, E2E, or Git writes. Explicit commands and changes of direction remain available.

## Handoffs

The agent has three phase-scoped handoff/decision helpers, inactive in ordinary Pi, plus the UI-only `workflow_ui_server` lifecycle tool. **`workflow_handoff`** takes `mode`, `input`, and optional short `notes`. Use an absolute saved plan/report reference, not the previous transcript. The helper dispatches `/workflow-handoff` internally to reach Pi's command-only session API, creates the fresh session, and starts the selected phase. It performs no approvals or artifact/check automation. Phase dispatch validates/reuses the task association; dispatching Plan outside a managed task uses the workspace setup described above.

**`workflow_question`** takes a question and at least two distinct nonblank option labels. It uses Pi's native selection: arrows to navigate, Enter to select, Escape to cancel. Supported RPC clients receive the standard select dialog. Print/JSON modes return the question/options for a chat answer instead. Selection returns the exact label; it never dispatches a phase or chooses a default. Escape/abort authorizes nothing: wait for chat without immediately reopening. Explicit chat answers remain valid. Free-form tasks, references, URLs, and substantive feedback stay in chat or the review surface.

- **Plan approval → Build:** normally review the saved plan with Plannotator's ordinary annotate tool (`gate: true`). Annotations stay in Plan for revision. Explicit browser or chat approval starts Build, carrying any guidance notes.
- **Authorized feature loop:** Build implements only the selected eligible feature and its checks, then automatically hands off with the same original plan to fresh independent feature Review. Scope is semantic, not a guessed Git diff boundary; shared files may contain multiple features. Review checks acceptance criteria, connected code/tests, and cumulative regression risks. In-scope findings automatically return to fresh Build for that feature, then fresh Review. Build validates findings rather than blindly applying them; disputed/unsupported findings retain evidence. A clean feature review records automated review status, not human approval, and goes directly to Build for the next eligible feature in plan order. No routine picker or browser interrupts these transitions.
- **Deferred blockers:** missing consequential decisions, required authority/input, or demonstrated inability to progress block only affected work/dependents. Repeating an unsuccessful approach without new evidence is not progress; there is no numerical retry cap. Record evidence, unresolved requirements/findings and affected dependencies; continue safe separable remainder and independent features, never claim partial work reviewed. Do not guess dependent decisions, bypass permissions, repeatedly retry blocked work, or silently accept findings as limitations.
- **Whole-plan loop:** when eligible feature work/reviews are exhausted, run fresh whole-plan Review over cumulative changes (or the explicit comparison scope), mapping every requirement to implementation/checks and inspecting integration, regressions, missed scope, and blockers. In-scope findings return automatically to focused Build then fresh whole-plan Review, including affected feature criteria. Partial work can be reviewed but cannot pass. Ask consolidated blocking questions only after independent work and applicable corrections are exhausted; substantive decisions stay in chat, finite navigation uses workflow_question. Answers resume the appropriate loop without another start confirmation; replan only when the resolution requires it. Only a whole-plan verdict without unresolved actionable findings, incomplete features, or blockers reaches human approval. Exclusions/accepted limitations need explicit authority and documented reasons.
- **Standalone Review findings:** standalone `/review` remains read-only; plans, reports, or numbered features do not imply implementation-loop authority. Show findings and ask **Plan or proceed** before routing; there is no extra findings-report approval gate. Plan independently revalidates findings. Review never fixes source.
- **Clean standalone or whole-plan Review:** use `workflow_question` with exactly **Review code in Plannotator**; **Approve code and go to UI**; **Approve code, skip UI, and go to Finalize**. Never automatically open code review. Direct approvals dispatch once to the named phase without another UI-or-Finalize question. Resolve the original implementation plan through the supplied reference/reports before UI/Finalize routing; ask if missing/ambiguous, never guess a latest plan or substitute a report.
- **Opt-in code review:** choosing the browser action alone approves nothing and routes nowhere. Open ordinary Plannotator code review with `gate: true` and the validated task checkout root explicitly supplied as `target` (not the source checkout or application subdirectory), explain silent-close/chat recovery first, then end the turn. Default scope is uncommitted changes; honor an explicit branch base and have the user verify the browser comparison because saved preferences can differ (use public `--diff-type uncommitted` when needed). After explicit browser approval, ask **UI or Finalize** unless the user already specified the destination. Human requests get a new standalone feedback report and the same **Plan or proceed** question; they are requests to revalidate, not proven defects or authority for new scope. Explain that proceeding leaves those requests unimplemented. Empty feedback without explicit approval, silent close, cancellation, failure, and unavailable UI approve nothing. Notes to UI/Finalize carry all known same-task clarification, feature-review, blocker, whole-plan review, human feedback and related artifact paths, including incoming references, plus material decisions and documented reasons for accepted limitations/deferrals. Earlier reports stay immutable until Finalize.
- **UI:** inspect the existing dev command/scripts, prerequisites, authority and external-data effects, then use the UI-only `workflow_ui_server` start/status/stop tool in the task/application directory. Use the actual unambiguous loopback HTTP URL without a routine URL question. Multiple/no URLs or startup/ownership failure require clarification/manual fallback; never guess/scan a port, install, migrate or start infrastructure. An explicitly supplied user-managed URL stays user-owned. Keep the owned process alive while human review waits; stop before any handoff/return. Human UI comments in annotations or chat get a report and automatically trigger changes, never a **Plan or ignore** picker. Small, clear, localized corrections within the existing design and authority go directly to a focused **Build ↔ Review → UI** loop: the unchanged original plan stays primary, the feedback report supplies supplemental acceptance criteria, and clean whole-plan Review returns directly to UI without another code-approval picker. Carry explicit correction-loop/return authority, all artifact references and the reviewed URL/route/ownership context in notes; never expand into next-feature work. Feedback requiring replanning, a consequential user decision or additional authority goes directly to Plan for research/questions. Comments are not approval, even when submitted with approval; requested changes must be addressed unless explicitly withdrawn/deferred. Explicit live approval or an explicit choice to skip/proceed starts Finalize with the original implementation-plan reference; forward known artifact paths and material decision guidance from Review along with any new UI feedback. Interactions can change real application data.
- **Finalize:** replace the current task's implementation plan with a standalone final decision record, verify it, then delete its other fully consolidated plan/review artifacts. Update only explicitly instructed journals/logs, verify Finalize's documentation changes against applicable formatting/lint rules after the last edit, and suggest one commit subject for the whole task. No extra routine approval gate or completion helper. With established task/publication authority, follow the signed commit/SSH push/gh PR sequence below, report the actual URL and return through workflow_exit; otherwise remain in the task unless explicitly asked to return.

If the next step is unclear, the agent uses `workflow_question` for finite choices with context and explicit consequences, or chat for free-form clarification. Plannotator remains the artifact/live-app review surface, not a bare approval picker. If it is unavailable/dismissed or its result is unclear, offer finite approve/retry/stop/skip/change-direction choices once the conversation resumes—never infer approval. A selection authorizes only its clearly described action. Already-authorized commands, Plan approval → Build, completed Build → Review, UI feedback → focused Build or Plan, clean UI-correction Review → UI, and live UI approval → Finalize get no extra picker gate. **Closing a normal Plannotator tab without sending feedback can send no message:** continue in chat when ready; there is no watcher/polling layer, and a silent browser close cannot wake a picker. Opening a review should explain that fallback beforehand.

Session creation/dispatch failures show the manual phase command. The helper also prints that command when requesting a handoff, since it does not track dispatch acknowledgements. Cancellation does not imply success; ordinary chat remains available. Concise notes travel with the handoff and are repeated in failure notices.

## Ordinary tools, short instructions

The editable `plan.md`, `build.md`, `review.md`, `ui.md`, and `finalize.md` prompts are reread for each request. They append guidance without replacing Pi's other instructions. Plan loads `plannotator`; Build loads `ponytail`; Review loads `ponytail-review` and `plannotator`; UI loads `plannotator`; Finalize requires no phase-specific skill. Full skill files, with their locations and relative-reference directories, are reread from the current session's discovered skills into the phase prompt on every request, including after resume/reload. Missing or unreadable skills/prompts warn and continue. Additional project docs are read only when relevant to the selected contract or a concrete missing-context/compatibility/safety question.

Use Pi's normal tools to read/write artifacts, inspect Git, run checks, and research. Explicit user/task paths or applicable project-owned workflow/agent instructions take precedence per artifact type: a path for one type does not redirect another. Otherwise use `~/.pi/plans/<project-key>/<task-id>.md` for Plans, `~/.pi/plans/<project-key>/<task-id>-<topic>.md` for Plan feedback, and `~/.pi/reviews/<project-key>/<task-id>-<topic>-<UTC timestamp>.md` for standalone Review and workflow UI/feedback reports. Use the validated association's `projectKey` (repository name plus canonical shared-Git-directory hash, or directory name plus canonical-root hash outside Git) and unique `id`, not the generated worktree basename or task prose. Artifact roots stay unchanged; no per-task directories are added. Exact original-plan/predecessor/report references remain authoritative, including older filenames and explicit paths outside those roots; do not rename or migrate them to fit defaults. Clarify conflicting/shared targets before overwriting and choose a new filename when a new report's default exists. Existing directories or historical files alone are not overrides. These are instruction-only defaults, not enforced locations; Pi's normal tools write the files. Expand `~` before calling filesystem tools unless they support tilde expansion. Plans/feedback reports must stand alone. Read before revising, preserve input reports/earlier reviews during Plan, Build, Review, and UI, and never revert user work automatically. Finalize has the bounded destructive exception below. In Git, Review covers staged, unstaged, and new files by default; explicit branch scopes need the user's base, not a guessed main. Explicitly pass the validated task checkout root to opt-in Plannotator code review, including when Pi's cwd is an application subdirectory. Use normal Plannotator comparison controls/commands and verify the browser scope; the public tool can inherit saved preferences.

### Final decision record and cleanup

Finalize consolidates **only the current task**, not the project. The existing implementation-plan filename survives as the summary under `~/.pi/plans/<project-key>/` unless explicit user/task or applicable project instructions override that artifact path. A report input must resolve unambiguously to its implementation plan. Read linked same-task plans, clarifications, reviews, and UI feedback and the paths carried in handoff notes; inspect relevant artifact directories for additional clearly related reports when needed. Establish exact eligible paths before editing. Similar filenames or modification times do not prove membership; do not bulk-read project history. Ask about ambiguous/shared artifacts, unreadable inputs, conflicting decisions, unclear targets, or unknown consequential outcomes/reasons before discarding contents. Linked source or external documents are not automatically cleanup targets.

Keep concise final choices and their documented reasons: merge duplicates, replace superseded proposals, and keep rejected alternatives only as useful rationale. Accepted limitations/deferrals and their reasons survive. Do not invent rationale or resolution. Omit procedural checklists, routing/review ceremony, raw test output, temporary notes, and redundant inventories. The record must stand alone without links to deleted files.

Fully read the eligible inputs, write the summary over the implementation plan, **read it back and verify decisions/reasons before deleting** the exact other identified, fully consolidated task artifacts. This deliberately loses detailed original history; there is no archive or recovery system. Never delete the summary, directories, unrelated/shared artifacts, source/config, journals, session logs, or Plannotator history. Failed write/readback/verification means no cleanup; partial deletion leaves the summary and remaining files intact and must be reported accurately, without claiming rollback. Repeated Finalize preserves existing decisions without duplicates or broader cleanup; no new inputs needs no substantive rewrite. Final output names the summary, cleanup results/limitations, journal status, and one subject. After documentation/bookkeeping edits, Finalize checks its changed files against applicable project formatting, Markdown, and documentation lint rules using existing installed, non-fixing checks, scoped where supported. Fix only issues it introduced within its allowed edit scope and rerun affected checks after the last edit; no installs, configuration changes, or unrelated reformatting. Where no automated check applies, inspect manually and say so. Report actual results, unavailable checks, and unresolved/pre-existing issues. Summary formatting must also be verified before artifact cleanup. Finalize still does not edit source, rerun tests or unrelated checks, install or change releases. Only after successful consolidation/scoped formatting checks does authorized publication begin; explicit return without publishing remains available through workflow_exit.

This safety sequence is instruction-based, not filesystem enforcement. Prompt-contract tests cannot prove semantic completeness, correct task membership, or a model's safe deletion behavior. Build/tests must not clean up real historical artifacts; any human consolidation smoke tests use disposable task inputs.

UI uses supported Plannotator tools/commands only. The public tool auto-detects a local live app but cannot force `--app`; if uncertain/unavailable, ask the user to run `/plannotator-annotate <url> --app --gate`. Do not substitute static approval for live UI approval. No private package imports, custom URL probes, or app automation. The UI-only owned-server helper takes an executable/argument array and absolute application cwd within the validated task, with no shell expansion or credential/environment parameters. It bounds in-memory output and URL candidates and returns URLs/status only, not raw logs. A URL needs a terminating whitespace/quote delimiter; unterminated output uses manual fallback instead of guessing a partial port/path. It owns an in-memory child/process group, not ports or persisted PIDs. POSIX process groups are required; unsupported ownership falls back to manual startup. Graceful stop escalates within bounded time and is idempotent; UI departure, tree navigation away, return, session replacement/reload and orderly shutdown clean up that owned group only. No server starts in the extension factory. Crash/forced kill and descendants deliberately escaping their group cannot guarantee cleanup. User-managed URLs require no lifecycle call and are never stopped. The dev command runs as the user, not in a credential sandbox; inspect scripts before starting and never inject credentials. Synthetic-process tests cover this facility without HTTP listeners, live apps or browsers.

There are no custom artifact/Git/check/UI runners, receipts/hashes, helper locks, worktree fingerprints, result polling, model settings, or code-level plan/commit validators. Role boundaries and successful routing rely on the agent following instructions, **not a sandbox or guaranteed model behavior**. You can steer or select another phase at any time.

Existing flat home-level and dotfiles-local plans/reports are grouped under `~/.pi/plans/dotfiles/` and `~/.pi/reviews/dotfiles/`, with references to relocated artifacts updated. Other historical content, approval files, and session logs are left untouched. The removed source/config/test files can leave obsolete Stow symlinks; remove only those stale links or restow the package. Never delete the approvals directory to reinstall.

## Authorized signed publication and recovery (managed Git only)

Finalize's `finalize.md` is the full ordinary-tool contract; there is no Git runner, publishing service, daemon or receipt system. Existing human approval of the implemented task authorizes publication without another routine gate. Missing authority or ambiguous scope/destination pauses only the affected action. Approval to implement/test this workflow does **not** authorize publishing or activating this implementation checkout.

- Inspect actual task cwd/branch/HEAD, staged contents, unstaged/new/deleted task files and existing task commits. Stage exact task-owned paths only; mixed hunks or unrelated index entries require clarification, not blanket staging or unstage/stash. External plans are not automatically commit content. Preserve unrelated work and exclude secrets/ignored local config.
- Create one signed task-wide Conventional Commit using `git commit -S` and existing GPG identity/hooks; reuse existing intended task commits without duplication, empty commits or history rewrite. Reconcile HEAD/status/commit contents after success, timeout or manual recovery. Hook mutations, unrelated commits/conflicts or leftover task work pause publication; never silently omit them.
- Prerequisites: the existing configured GPG signing key/agent/cache, existing SSH publishing remote with a usable ssh-agent at Pi's SSH_AUTH_SOCK, and **separate existing gh authentication** for API/PR operations. Accessible same-user agents are not agent-private authority. No token/HTTPS migration, credential retrieval, gh login/setup-git automation, remote rewrite, global settings change or secret logging.
- If GPG locks/expires or pinentry fails, Pi pauses for you to sign harmless text in your terminal, then waits for confirmation. Resolve the non-secret Git `user.signingkey` and configured signing program first; do not assume GPG's default key. A fish/POSIX example is `printf '%s\n' 'Pi signing cache unlock' | gpg --local-user '<configured signing key>' --clearsign > /dev/null`, with the actual key safely substituted and the same GNUPGHOME/agent environment. GPG has no per-command cache lifetime like ssh-add: existing default-cache-ttl/max-cache-ttl and signing/cache policy control expiry. No dummy commit, passphrase-preset/loopback handling, agent-policy changes or unsigned fallback. If automation remains impossible, make the signed commit manually in the task terminal and confirm; Pi verifies before continuing.
- If SSH's key is locked/unloaded, Pi pauses for a user-run `ssh-add -t 1h <chosen key path>` (explicit example lifetime; use your chosen duration/path), then waits for confirmation. Keep the same SSH_AUTH_SOCK; starting another shell's agent does not update Pi. Missing/mismatched sockets, unknown host identity and authorization failures require the right diagnosis, not blind unlock retries. Never inspect private keys or weaken host/touch/confirmation policy. Manual normal push is a recovery option. Missing gh login/access separately requires user terminal authentication and confirmation, without token/password disclosure.
- Resolve SSH push remote, GitHub host/repository, head and base explicitly; ambiguity/forks/multiple destinations pause. Base defaults to GitHub's repository default branch, not launching HEAD/branch or guessed main; honor an explicit base. Push only the task branch with a normal explicit `refs/heads/<task>:refs/heads/<task>` refspec. Verify `git ls-remote --heads` equals local HEAD before PR creation or retry. No force/delete/mirror/base push, automatic fetch/pull/rebase/merge or automatic fork.
- Find matching PRs across all states with explicit repository/head/base; verify repository, branch, commit, base and ready/open state. Reuse an exact open ready-for-review match. Draft/closed/merged/ambiguous matches require direction, never silent reopen/duplication. Otherwise use normal `gh pr create` with explicit repo/head/base/title/body, concise summary/actual checks/limitations and no private artifacts. Explicit head avoids implicit gh push/fork. Never use create's dry-run as a safety check: it can push. Query state after uncertain create before retrying, then verify the actual resulting PR.
- Recovery retries only the unresolved step after confirmation and actual-state reconciliation. Cancellation/failure preserves files/index and any already-pushed branch; stay in the task with the exact recovery point, not a rollback or success claim. Report the verified PR URL **before** returning to the original cwd in fresh ordinary Pi. Return failure retains the URL/recovery paths. A bare exit always returns without publishing. No CI polling, automatic merge, local-main update, branch/worktree deletion or production activation; you wait for CI and merge on GitHub.

These publication contracts and their failure boundaries are prompt-tested, not an enforced Git transaction or a guarantee of model compliance. Transport tests use a synthetic PR URL only; no credentials, signing, API or remote operations.
