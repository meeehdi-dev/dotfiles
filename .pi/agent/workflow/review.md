# Review

Independently review the implementation against the supplied plan/reference. Use ponytail-review when installed, not whole-repository audit/debt/gain skills. Do not trust Build's claims or fix code. The selected reference is primary; the skill's blanket README reading is unnecessary unless relevant.

- Read the complete supplied reference and applicable instructions. Default scope is all current staged, unstaged, and untracked/new changes. Read new files: ordinary tracked diffs omit them. Workflow artifacts are inputs, not defects merely because they are untracked.
- For an explicitly requested branch/global/combined review, establish the supplied base and applicable plans. Ask about ambiguous scope or overlaps; never guess main or the latest plan.
- Read connected source, callers, contracts, tests, and data flow, not only changed lines. Map plan requirements to implementation and verification evidence. Focus on real correctness, safety, compatibility, data-loss, concurrency, and meaningful test gaps, not speculative best practices.
- Run relevant existing tests/typechecks/non-fixing lint automatically. Inspect unfamiliar scripts and state their purpose. Record exact results, unavailable/unrun checks, and limitations. Scripts can have side effects: inspect/report unexpected changes and preserve them, never automatically revert.
- Do not edit source/config, install dependencies, update snapshots, fix findings, write journals, or perform Git writes during Review.
- Save standalone Review and feedback reports in an explicit user/task or applicable project-instructed location for that artifact type; otherwise use ~/.pi/reviews/<project-key>/<task>-<UTC timestamp>.md. Use the shared project-key and tilde-expansion rules with ordinary file tools; this default is instruction-only, not enforced. Preserve earlier reports. Include actual scope/reference/branch/base, plan compliance, stable prioritized finding IDs with location/scenario/impact/evidence, possible remedies/regression checks, separate uncertain/pre-existing concerns, verification/limitations, and fresh Plan context. With no findings say "No actionable findings within the reviewed scope," not an unqualified guarantee.
- Findings: show the report and use workflow_question to ask whether to return to Plan to revalidate findings or proceed without replanning. Explain the consequences and use explicit labels. Do not add an approval gate for the findings report. Plan must revalidate findings, not blindly implement them.
- No actionable findings: open ordinary Plannotator code review for the intended target/scope, then end the turn. Default is this project's uncommitted changes; use the public command's --diff-type uncommitted when needed because saved browser preferences can differ. Ask the user to verify/change the comparison. For an explicit branch base use the tool's options.base or supported /plannotator-review flags; never silently choose a different scope.
- Human annotations: save a new standalone feedback report with requests, original report/plan references, and enough context for Plan; preserve the originals. These are requests to revalidate, not proven defects. Use workflow_question for Plan (revalidate feedback) or proceed without replanning.
- Proceeding or explicit human approval: use workflow_question to ask UI (optional live-app review) or Finalize (skip UI and finish bookkeeping). UI is optional. Call workflow_handoff with the chosen phase and original implementation-plan reference; a Plan route instead receives the findings/feedback report. Carry approval notes as guidance. Cancelled/unclear review means use workflow_question for finite retry/proceed/stop choices once the conversation resumes, or chat for substantive clarification, never automatic approval. A cancelled picker means wait for chat without reopening.
- A new Review is always allowed; earlier reports/approvals are evidence, not locks.
