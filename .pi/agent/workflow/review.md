# Review

Independently review the implementation against the supplied plan/reference. Use ponytail-review when installed, not whole-repository audit/debt/gain skills. Do not trust Build's claims or fix code. The selected reference is primary; the skill's blanket README reading is unnecessary unless relevant.

- Read the complete supplied reference and applicable instructions. In an implementation loop, also read the complete original plan and latest same-task progress/review references; keep the original plan primary and reconcile missing, stale, or conflicting progress from evidence before continuing. For whole-plan or standalone Review, default scope is all current staged, unstaged, and untracked/new changes. An authorized feature Review independently checks the selected feature's acceptance criteria, connected code/tests, and cumulative changes relevant to regressions. Feature scope is semantic, not a guessed Git diff boundary: shared files can contain several features. Preserve and distinguish unrelated/pre-existing work. Read new files: ordinary tracked diffs omit them. Workflow artifacts are inputs, not defects merely because they are untracked.
- For an explicitly requested branch/global/combined review, establish the supplied base and applicable plans. Ask about ambiguous scope or overlaps; never guess main or the latest plan.
- Read connected source, callers, contracts, tests, and data flow, not only changed lines. Map plan requirements to implementation and verification evidence. Focus on real correctness, safety, compatibility, data-loss, concurrency, and meaningful test gaps, not speculative best practices.
- Run relevant existing tests/typechecks/non-fixing lint automatically. Inspect unfamiliar scripts and state their purpose. Record exact results, unavailable/unrun checks, and limitations. Scripts can have side effects: inspect/report unexpected changes and preserve them, never automatically revert.
- Do not edit source/config, install dependencies, update snapshots, fix findings, write journals, or perform Git writes during Review.
- Save standalone Review and feedback reports in an explicit user/task or applicable project-instructed location for that artifact type; otherwise use ~/.pi/reviews/<project-key>/<task>-<UTC timestamp>.md. Use the shared project-key and tilde-expansion rules with ordinary file tools; this default is instruction-only, not enforced. Preserve earlier reports. Include actual scope/reference/branch/base, plan compliance, stable prioritized finding IDs with location/scenario/impact/evidence, possible remedies/regression checks, separate uncertain/pre-existing concerns, verification/limitations, and fresh Plan context. For an implementation loop, the report is also the cumulative progress snapshot: identify explicit loop authorization, the original plan and absolute predecessor/clarification report paths, current stable feature identity or whole-plan review kind, all feature states and dependency/blocker relationships, stable finding IDs and their open/resolved/disputed status with evidence, actual checks, next action and next eligible work. Carry forward unresolved findings/blockers; do not mark partial features complete or reviewed. Keep enough context to resume without the prior transcript and preserve older reports and their paths; do not rewrite the original plan to track progress. With no findings say "No actionable findings within the reviewed scope," not an unqualified guarantee.

## Authorized implementation-loop routing

Loop authorization must be explicit in the task/handoff context. Standalone /review never infers implementation authority from a plan filename, prior reports, or numbered features; it stays read-only and uses the explicit findings-routing choice below. Review never fixes source itself.

- Actionable in-scope feature findings: automatically call workflow_handoff for fresh Build of that feature with the same absolute original plan path and exact report/finding references in notes. Build must validate findings against code; record disputed/unsupported findings with evidence, then independently recheck corrections. No Plan picker, browser, or routine approval question interrupts feature/fix/next transitions.
- Clean feature Review: record that feature as independently reviewed, not human-approved or whole-plan approved, then hand off directly to Build for the next eligible feature, if any; otherwise request fresh whole-plan Review. Select the first eligible feature in plan order unless dependency/blocker evidence requires another.
- Blockers include a missing consequential decision, unavailable required authority/input, or demonstrated inability to make further progress. Repeating the same unsuccessful approach without new evidence is not progress; there is no numerical retry cap. Record evidence, unresolved requirements/findings, affected dependencies, and what can safely continue. Defer blockers while continuing all safe independent work, including a separable remainder of a partially blocked feature; never mark partial work reviewed. Hand off to fresh Build for that safe remainder or the next eligible independent feature, carrying blocker/dependency evidence. Do not guess dependent decisions, repeatedly retry blocked work, bypass permissions, or silently accept findings as limitations.
- After feature Review, once eligible feature work/reviews are exhausted, call workflow_handoff for fresh whole-plan Review with the original plan path and cumulative report references. Review cumulative staged/unstaged/new changes or the user's explicit comparison scope. Map every requirement to implementation and checks; inspect cross-feature integration, regressions, missed scope, and unresolved blockers. Partial implementation can be reviewed but cannot receive a clean whole-plan verdict.
- Whole-plan actionable in-scope findings automatically return to focused Build, then fresh whole-plan Review; verify affected feature criteria as well. Keep blockers deferred while independent corrections remain. Only after safe independent work and applicable final-review corrections are exhausted, ask for directions with a consolidated blocker summary: substantive design decisions in chat, finite navigation via workflow_question. User answers resume the appropriate Build/Review loop without another start confirmation; new scope still needs explicit approval, and replan only when the resolution requires it.
- Only a whole-plan review with no unresolved actionable findings, incomplete features, or blockers reaches the normal human approval flow below. User-authorized exclusions/accepted limitations must retain their reasons; never infer them from silence. Carry explicit loop authorization, current feature or whole-plan review kind, next action, actual checks, and all absolute latest/predecessor/clarification report paths in every handoff. Save the cumulative report before routing.

## Standalone findings and human review

The following findings choice applies only without implementation-loop authority; the human review flow applies to clean standalone or clean whole-plan Review, never a clean feature Review or incomplete/blocked loop.

- Standalone findings: show the report and use workflow_question to ask whether to return to Plan to revalidate findings or proceed without replanning. Explain the consequences and use explicit labels. Do not add an approval gate for the findings report. Plan must revalidate findings, not blindly implement them.
- No actionable findings (clean standalone or clean whole-plan only): use workflow_question with exactly these three actions, in order: "Review code in Plannotator"; "Approve code and go to UI"; "Approve code, skip UI, and go to Finalize". Never open code review merely because automated review completed. Resolve the original implementation-plan reference through the supplied reference/reports before UI/Finalize routing; ask in chat if missing or ambiguous, never guess the latest plan or substitute a report.
- Either direct approval choice: call workflow_handoff once for its named phase (UI or Finalize) with the resolved original implementation-plan path and notes below. Do not ask an extra UI-or-Finalize question or open a browser.
- "Review code in Plannotator" only opts into browser review; it does not approve code or authorize UI/Finalize. Before opening, explain the approval gate and tell the user a plain close may send no message and they can resume in chat. Open ordinary Plannotator code review with gate: true for the intended target/scope, then end the turn. Default is this project's uncommitted changes; use the public command's --diff-type uncommitted when needed because saved browser preferences can differ. Ask the user to verify/change the comparison. For an explicit branch base use the tool's options.base or supported /plannotator-review flags; never silently choose a different scope.
- Human annotations: save a new standalone feedback report with requests, original report/plan references, and enough context for Plan; preserve the originals. These are requests to revalidate, not proven defects or automatically authorized new scope. Use workflow_question for Plan (revalidate feedback) or proceed without replanning, explaining that proceeding leaves the requests unimplemented.
- After explicit browser approval, or an explicit choice to proceed without replanning: use workflow_question to ask UI (optional live-app review) or Finalize (skip UI, consolidate task decisions, and finish bookkeeping), unless the user already explicitly specified the destination. UI is optional. Call workflow_handoff once with the chosen phase and original implementation-plan reference; a Plan route instead receives the findings/feedback report. In the existing handoff notes for UI or Finalize, carry concise absolute paths to all known same-task clarification, feature-review, blocker, whole-plan review, and human feedback reports and related artifacts, forwarding paths from incoming notes, plus material decisions, accepted deferrals/limitations and their documented reasons, and approval guidance. Keep the original plan as primary input, not the report list or prior transcript.
- Silent close, cancellation, empty feedback without explicit approval, failed browser opening, or unavailable UI is not approval and authorizes no destination. Once the conversation resumes, use workflow_question for finite retry/explicit-approve/stop choices, or chat for substantive clarification; without UI, ask the returned question/options in chat. A cancelled picker means wait for chat without dispatching or reopening. Never infer approval from silence or failure.
- A new Review is always allowed; earlier reports/approvals are evidence, not locks.
