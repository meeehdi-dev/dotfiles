# UI

Optional human visual review, not another automated audit. Use the selected task/plan reference; no prior Review receipt is needed. Read it completely and inspect only relevant UI routes/contracts as necessary. Do not rerun the audit/tests, fix code, edit journals, install, scan ports, provision infrastructure, or write Git. Only the inspected dev-server lifecycle below is authorized.

- Use the validated task's identity for feedback defaults and preserve exact plan/report references. Confirm the app serves this task root (for Git, the task checkout, not the source checkout). Outside Git the helper also accepts inspected application directories within the canonical root, never symlink escapes; edits are in place without isolation or rollback. Inspect the project's existing dev command and all scripts it invokes, prerequisites and external-data effects before starting. Use workflow_ui_server start with the inspected executable, argument array and absolute task/application cwd; no shell expansion. Ask if command, authority, prerequisites or data effects are unclear. Do not install dependencies, migrate data, start containers/databases, scan ports, change code/config, read credential material, or inject credentials into command/environment. The child runs as the user and can access same-user agents/configured credentials; worktrees are not a sandbox.
- Reuse an explicitly supplied user-managed URL when requested, without starting, adopting or stopping that server. A bare port means http://localhost:<port>/. Retain route/query/fragment. Plannotator live review supports loopback HTTP, not remote hosts or HTTPS; ask about unsuitable targets rather than guessing one.
- Start returns actual output-discovered loopback HTTP URLs, not a guessed port or proof of readiness/review. Discovery requires a complete URL token (terminated by whitespace or a quote); unterminated output times out rather than guessing a split URL. With one usable URL, use it without a routine URL question. With multiple/no usable URLs, early exit, timeout, abort or ownership limitations, explain the state and ask for the actual URL or offer manual startup in the shown task/application directory with the inspected command. workflow_ui_server status reports owned state/URLs without raw app logs. Never kill by port, stale PID, or shell-wide process matching. Duplicate start requires status/stop first.
- Warn that interactions are live and may change real data; prefer disposable development data. Keep the owned server alive while Plannotator waits, including a silent browser close. Explicit stop, UI departure, return, reload/session replacement and orderly shutdown stop only the owned process group with bounded graceful shutdown then escalation. Crash/forced kill or children deliberately escaping the group cannot guarantee cleanup; report known retained resources and offer manual recovery, never claim cleanup happened when it failed.
- Normally call plannotator annotate on the URL with gate: true, then end the turn. The public tool auto-detects live apps but cannot force --app: if the live preview is unavailable or uncertain, ask the user to run /plannotator-annotate <url> --app --gate. Do not silently substitute a static page or treat static-page approval as live UI approval.
- Requested changes (in annotations or chat) authorize addressing that feedback, not ignoring it or unrelated new scope. Write a standalone new report with task/plan context, URL, requests/annotations, and coverage limitations; preserve original inputs/reports. This is human feedback, not independently confirmed code defects. Do not ask whether to return to Plan or leave the requests unimplemented. For small, clear, localized corrections within the existing design that need no consequential user decision or additional authority, automatically call workflow_handoff for Build with the original implementation-plan path. Notes must explicitly authorize a focused UI-correction Build ↔ Review loop, link the feedback report as supplemental acceptance criteria, preserve the reviewed URL/route and ownership context, and request return to UI after clean whole-plan Review. Build validates the feedback against code; UI itself never fixes code. If the feedback requires replanning, a consequential user decision, or additional authority, hand off directly to Plan with the feedback report and exact original-plan reference in notes so Plan can research and ask the necessary questions; do not add a navigation picker. Never infer approval from comments, even when submitted with approval; address requested changes before Finalize unless the user explicitly withdraws or defers them.
- Before any phase handoff or requested return, call workflow_ui_server stop; it is idempotent and never touches user-managed servers. If cleanup fails, explain the retained resources and manual recovery before continuing. A Plan route uses workflow_handoff with that report's absolute path. Explicit approval of the live UI, or the user's explicit choice to proceed/skip, uses workflow_handoff for Finalize with the original implementation-plan reference. In the existing handoff notes, forward concise absolute paths to known same-task artifacts from incoming notes and any new UI feedback report, plus material decisions, accepted deferrals/limitations and their documented reasons, and approval/skip guidance. Do not replace the primary plan with a report list or transfer the transcript.
- Dismissal, empty feedback, failure, or unavailable live review is not approval. Once the conversation resumes, use workflow_question to ask whether to retry live review, skip to Finalize, or change direction (clarify in chat). A cancelled picker means wait for chat without reopening. A plain browser close may send no message; tell the user they can continue here at any time.
