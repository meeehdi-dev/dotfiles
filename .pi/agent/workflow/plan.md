# Plan

Investigate and agree on a standalone implementation plan, not an implementation. The input can be a new task or a report; interpret its meaning, not its filename suffix. Read supplied documents completely. If the input or goal is unclear, ask; do not invent defects in an arbitrary document. Never overwrite an input report with the output plan.

- Read applicable instructions and relevant source, callers, tests, interfaces, and history. Use non-mutating research; do not implement, run tests, install, migrate, manage services, or deploy during planning.
- Establish the goal, observable behavior, constraints, scope, and non-goals. Include only user-requested or explicitly user-approved scope. Derive necessary implementation steps and checks without per-file/test approval; do not treat recommendations, inferred preferences, or unrelated improvements as requirements. Challenge unnecessary complexity/dependencies.
- After research, grill consequential missing details, assumptions, and discretionary recommendations the code cannot settle. If any exist, save a separate clarification document using the Plan feedback artifact rules below. Use contextual Plannotator question blocks: explain consequences, give a recommendation and rationale when applicable, and offer rejection of optional additions. Open it with the installed plannotator tool, end the turn, and wait for answers; follow up only on remaining consequential uncertainty. If no real questions exist, proceed directly to normal plan review; never invent a grilling round.
- Include a proposed addition only after an explicit answer or approval clearly covers that proposal. Silence, skipped questions, dismissal, tool failures, or approval of another item authorize nothing. Keep unanswered or rejected proposals out of implementation scope; pause if an unanswered question blocks requested behavior. Record settled decisions in the standalone plan. Never use final plan approval to retroactively legitimize silently inserted scope.
- Planning clarification and proposed-scope questions use Plannotator, not workflow_question or automatic chat fallback; this specific rule overrides generic question-routing/fallback guidance for those questions. If Plannotator is unavailable, pause unresolved scope decisions until it works or the user explicitly authorizes another channel. Closing without answers chooses no default and authorizes no handoff. Workflow navigation still uses workflow_question for finite choices and chat for free-form direction; final plan approval remains separate below. Opening or answering a grilling document neither approves the implementation plan nor authorizes Build.
- For a findings/feedback report, independently classify every issue: confirmed, incorrect/not applicable, needs clarification, or proposed deferral. Explain the evidence and agree on exclusions rather than silently dropping confirmed issues.
- Resolve consequential decisions before presenting the plan as ready. Include scope/non-goals, current-state evidence and references, decisions/rationale, identifiable requirements and acceptance criteria, an ordered checklist with affected files/interfaces, validation commands/cases, risks/stop conditions, and a concise fresh-session Build handoff. Map report findings to steps or agreed exclusions. Be descriptive: no implementation snippets, code blocks, or pseudocode. Be complete, not ceremonial.
- Keep one original plan with numbered features and stable feature identifiers, acceptance criteria per feature, ordered implementation steps, and explicit dependencies where they exist. Do not turn each file or test into a feature or split features into separately approved plans. A single-feature or older unnumbered plan remains usable as one implementation unit; clarify only genuinely ambiguous feature divisions or dependencies. These identities are the durable Build/Review handoff contract, not a progress checklist to rewrite during implementation.
- Save the plan (and any Plan feedback report) in an explicit user/task or applicable project-instructed location for that artifact type; otherwise use ~/.pi/plans/<project-key>/<task>.md. Use the shared project-key and tilde-expansion rules with ordinary file tools; this default is instruction-only, not enforced. Normally open that file with plannotator annotate and gate: true. End the turn and wait. Revise/resubmit when annotations arrive; ask about conflicts or unanswered consequential questions.
- Explicit browser or chat approval: call workflow_handoff for Build with the saved plan's absolute path and any guidance notes. Never infer approval from silence, dismissal, or an error; use workflow_question for finite retry/stop choices once the conversation resumes, or chat for clarification. A cancelled picker means wait for chat. Do not implement here.
