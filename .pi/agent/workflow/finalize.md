# Finalize

Consolidate the current task's final decisions and perform instructed bookkeeping. Outside Git follow the non-Git completion rule below. For managed Git tasks, when implementation authority is established, ask whether to merge locally in-place (no push) or create/reuse a GitHub PR, prepare a signed task commit, complete the chosen route, then return to ordinary Pi. A direct chat request for Finalize or an authorized handoff is sufficient instruction to start; do not ask for another routine approval, browser review, receipt/hash/provenance check, worktree comparison, or clean index. Documentation-only Finalize remains available without publication; Git inspection is required before publication, not before consolidation.

- If given a report, resolve its actual implementation plan through its references; ask if the target plan is ambiguous or missing. Keep the existing implementation-plan path as the surviving summary under the shared artifact rules. Consult source/history only as needed to understand the whole implemented task; do not claim checks were rerun here.
- Follow the publication sequence below only with established authority; documentation-only Finalize grants none. Establish a concrete set of eligible source paths before editing: only the current task's implementation plan, related plans, clarifications, reviews, and UI feedback. Read these inputs completely, following task-related references and paths in handoff notes, not every historical link. Inspect relevant project artifact directories when needed for clearly related reports that reference the plan but are not linked from it. Do not bulk-read project history or infer membership from filename prefix or modification time alone. A linked file outside normal artifact folders is not automatically eligible for deletion.
- Ask before discarding contents when task membership, shared artifacts, target paths, conflicting decisions, unreadable inputs, or relevant outcomes/reasons remain unclear. Preserve work and continue in this session after clarification; do not invent rationale, treat proposals as approval, or call unresolved findings fixed.
- Replace the implementation plan with a concise standalone final decision record identifying the task and its final choices with documented reasons. Merge repeated choices, replace superseded proposals with the final position, and keep rejected alternatives only when they explain that position. Retain accepted limitations and deferred findings with their reasons. Exclude implementation checklists, session routing, review ceremony, raw test output, repeated findings, temporary investigation notes, and redundant source inventories. Do not leave links to artifacts being deleted.
- Fully read and consolidate all eligible inputs before replacing the plan. Write the complete summary at the target plan path, then read it back and verify that the sources' final decisions and reasons are accurately represented and applicable formatting rules are respected. Only after successful verification delete the exact other task artifact paths already identified and fully consolidated. This is the Finalize-only exception to preserving input reports and earlier reviews; it intentionally removes detailed history without an archive. Never delete the surviving summary, parent directories, unrelated/shared artifacts, source/configuration files, journals, session logs, or Plannotator history.
- If summary write/readback or verification fails, perform no cleanup. If deletion partially fails, preserve the summary and remaining files and report exactly what remains; clarify when needed and continue here. Do not promise transactional rollback or automatic recovery. On repeated Finalize, read the existing summary, preserve its decisions, avoid duplicate entries and unrelated cleanup; no new task inputs means no substantive rewrite.
- Update only journals/logs explicitly required by applicable instructions, at their named locations and in the existing format. Read targets first, preserve entries, avoid duplicates on resumption, and use the time actually written. Create a required log only when its creation/location is instructed. Existing logs alone are not authorization. If no journals are required, skip journal writes and ask no journal-location question. Ask about genuinely ambiguous/unreadable required bookkeeping. Consolidation and journal updates need no automatic new review.
- After any documentation/bookkeeping edits, verify all files changed in Finalize against applicable project formatting, Markdown, and documentation lint rules. Inspect existing configuration/scripts first; run relevant installed checks in non-fixing mode, scoped to those files where supported. Correct only formatting/lint issues introduced by Finalize within its allowed edit scope, then rerun the affected checks after the last edit. Do not install tools, change configuration, or reformat unrelated content. If no automated check applies, inspect the changed text against the applicable rules and state that verification was manual. Report actual results, unavailable checks, and unresolved or pre-existing issues; do not claim earlier checks cover later edits. If summary formatting verification fails, perform no artifact cleanup.
- Suggest exactly one single-line Conventional Commit subject for the complete task from its start, not only final fixes, UI follow-up, or journals. Features normally use feat and repairs fix; follow repository type/scope/length conventions without inventing a universal length limit. No body, footer, trailer, wrapper, or Git command in the subject.
- Use a breaking marker only for an actual consumer-facing break in a positively identified public library/package. A manifest alone is insufficient; standalone and unknown projects do not use it. Do not bump versions or edit releases.
- Do not edit source, instructions, or unrelated docs; edit plans/reports only for the consolidation above. Do not run tests, unrelated checks, or installs, or reopen Plannotator as an automatic final phase; only the scoped documentation formatting/lint checks above are automatic. Only the task-scoped staging, signed commit and selected local-merge or normal SSH push/gh PR route below are Git-write exceptions; verified local-merge return may remove the task worktree without force, retaining its branch. Only the return helper may run ignored-only git clean -fdX after successful verified local-merge return; no agent-run clean. No amend, reset/stash, history rewrite, hook bypass, Git configuration changes, or unrelated index changes. Never invent a commit/hash.
- Finish with the summary path, cleanup results or exact remaining artifacts/limitations, journal paths updated or "no journals required," formatting/lint verification results and any evidence limitations, and the one suggested subject. For documentation-only Finalize in Git, remain in this session unless explicitly asked to exit. Authorized completion follows below with a merge-or-PR choice, not another code-approval gate.

## Non-Git completion

Perform the same bounded consolidation, bookkeeping and scoped documentation verification above without any Git status/diff/commit, push, PR, signing or authentication work. After successful consolidation and checks, report the summary, cleanup/journal/check outcomes, limitations and suggested subject, then automatically call workflow_exit once without publicationUrl and end the turn. Incomplete or failed consolidation, required bookkeeping, cleanup or formatting verification stays in this session for recovery; explicit exit remains available independently. Never accept publication context or adopt a repository that appeared later; pause for direction instead.

## Authorized publication — managed Git tasks only, ordinary Git and gh tools

These are agent instructions, not a publishing runner or an approval receipt. Shared commit preparation serves both routes; remote publication steps apply only to the PR choice. Use argument-safe commands in the validated task checkout (the source checkout only for the selected local merge); quote resolved paths/refs for the actual shell, never interpolate task prose as shell syntax. No signing/authentication probe or remote operation belongs in implementation tests.

1. **Authority and scope.** Establish implementation/publication authority from the task and explicit human code/UI approval or direct publication instruction, not task metadata, a standalone Review, a documentation-only Finalize, or automated review success. If absent, finish documentation only and explain what authority/scope is missing. Existing human approval of the implemented task permits commit preparation without a new routine publication gate, but never chooses the completion route. Before staging, use workflow_question with exactly two actions in order: "Merge in-place (local only, no push)"; "Create or reuse a PR on GitHub". Explain that local merge updates the original checkout's local base, keeps the task branch, discards all ignored task files and removes the verified merged task worktree after successful return, and leaves pushing manual; PR mode pushes only the task branch. Skip the picker only when the user already explicitly chose a route for this task. Cancellation/abort means wait for chat without choosing a default or reopening; without UI ask in chat and wait. Stop if consolidation, required bookkeeping or scoped formatting verification is incomplete/failed. Stop any owned UI server before publication (UI departure normally already did so).
2. **Inspect before staging.** Verify actual cwd, repository, task branch and HEAD against the validated association; never publish from the source checkout or base branch. Inspect `git status --porcelain=v1 --untracked-files=all`, `git diff`, `git diff --cached`, and task commits since the recorded starting commit. Establish exact task files and hunks, including additions/deletions and relevant Finalize edits inside the checkout. External artifacts are not automatically commit content. Inspect new files before inclusion; exclude secrets, ignored local configuration and unrelated changes. Mixed task/unrelated hunks or pre-existing unrelated staged contents require clarification; do not silently unstage, stash or commit them. Use scoped `git add -- <exact task paths>` only when each full path is task-owned; never blanket-stage with `git add .`, `-A`, or `commit -a`. Inspect the full staged diff again before committing.
3. **One signed task commit.** Choose exactly one task-wide Conventional Commit subject as above. Use `git commit -S -m <subject>` with the existing configured OpenPGP identity and normal hooks; inspect non-secret `user.signingkey`, `gpg.format` and `gpg.program` configuration as needed. Missing/ambiguous key or a different signing mechanism requires direction, not identity/config changes. Use the existing gpg-agent cache first with a bounded command timeout. Never disable signing, bypass hooks or use an unsigned fallback. No staged changes means no empty commit. Reuse existing user-made task commits when they already contain the intended scope, without duplication, amend or rewriting history. Inspect commit contents/signature information and remaining staged/unstaged/untracked task work after success as well as failure; missing/invalid task signatures, hook mutations, unrelated commits, conflicts or incomplete task files pause publication. Do not treat a reported manual commit as signed without checking; do not rewrite an unsigned existing commit without direction. Do not silently leave task work out of the selected completion route.
4. **GPG recovery pauses.** Password, touch and pinentry prompts belong to GPG or the user's own terminal, never chat/tool parameters. On locked/expired cache, unavailable pinentry or timeout, ask the user to unlock the configured Git signing key in their terminal with a harmless signature, then wait for confirmation. Generate the instruction for their actual shell and configured key/program, using the same GNUPGHOME/agent environment as Pi. For fish, an example after resolving the key is `printf '%s\n' 'Pi signing cache unlock' | gpg --local-user '<configured signing key>' --clearsign > /dev/null`; POSIX shells support the same pipeline. The placeholder is not a command to run unchanged; safely quote the actual non-secret key. No dummy Git commit, private-key inspection, passphrase-preset, loopback-secret handling, agent restart or configuration edit. GPG has no ssh-add-style per-command cache-duration option: existing default-cache-ttl/max-cache-ttl and signing/cache policy control expiry. If environment/policy still prevents automation, offer a user-run signed commit in the task terminal, preserving hooks and signing.
5. **Resume only after confirmation.** Cancellation/failure preserves files/index and stays in the task; offer explicit exit without publishing. After unlock or a reported manual commit, inspect actual branch, HEAD, commit contents/signature and status before retry. A timed-out commit may already exist. Retry only the unresolved step with new evidence, never indefinitely or from the beginning; unexpected state requires direction. Manual commit success is verified, not inferred from chat. No leftover task work is silently dropped.
After step 5, local-merge choice follows **Local merge** below and skips steps 6–9 entirely: no push, remote/gh calls or SSH authentication. Only the PR choice continues below.

6. **Resolve destination and separate gh authentication.** Resolve the selected existing SSH remote's push destination, GitHub host/repository, head branch and base explicitly. Multiple remotes/push URLs, forks, non-SSH destinations or uncertain repository/base require clarification; never rewrite remotes, create a fork or migrate to HTTPS/tokens. Use existing gh authentication for repository metadata/API, separately from SSH-agent access. If gh is unauthenticated or lacks access, ask the user to authenticate in their terminal and confirm; never automatically run gh login/setup-git or retrieve/display credentials. No `gh auth token`, secret environment dump or credential-debug output. Resolve the repository default branch through gh metadata (for example `gh repo view <host/owner/repo> --json defaultBranchRef`); use an explicit user-requested base instead. Never substitute the launching branch, branch-specific gh defaults or guessed main. If metadata/base cannot be resolved, pause.
7. **Normal SSH push only.** Use the existing SSH_AUTH_SOCK and unlocked ssh-agent, preserving host verification, hooks and confirmation/touch policy. Push only the recorded task branch with an explicit normal refspec: `git push <selected remote> refs/heads/<task branch>:refs/heads/<task branch>`. No force, mirror, delete, base-branch push, automatic fetch/pull/merge/rebase or hidden rejection repair. On locked/unloaded SSH key, ask the user to run a timed `ssh-add -t 1h <chosen key path>` in their terminal (1h is an explicit example lifetime; honor their chosen lifetime/path), then wait for confirmation. Do not inspect private keys. The terminal must use the same SSH_AUTH_SOCK as Pi; a new agent in another shell does not update Pi. A missing/mismatched socket, unknown host identity, authorization failure or divergent push needs its actual diagnosis, not a misleading unlock retry. If unlocking cannot work, offer manual normal push, then verify it. After any uncertain push or manual recovery, compare `git ls-remote --heads <selected remote> refs/heads/<task branch>` with actual local HEAD before retry or PR creation. If the remote's fetch URL differs from its resolved SSH push URL, verify against the push URL, not the fetch destination; multiple push destinations still require direction. A missing/mismatched published head pauses; never claim push success from exit status alone.
8. **Find or create the PR.** Only after the exact published head is verified, query existing PRs with explicit repository/head/base and all states, for example `gh pr list --repo <host/owner/repo> --head <task branch> --base <resolved base> --state all --json number,url,state,isDraft,headRefName,headRefOid,baseRefName,headRepository`. Verify head repository/branch, head commit and base match; ambiguity requires direction. Reuse an exact matching open ready-for-review PR. A draft, closed or merged match requires direction; do not silently reopen, duplicate or change its state. Otherwise create a normal ready-for-review PR with `gh pr create --repo <host/owner/repo> --head <task branch> --base <resolved base> --title <task title> --body <summary>`. Explicit head avoids implicit push/fork behavior; never use `gh pr create --dry-run` as verification because it may push. Include a concise task summary, actual checks and material limitations, not private plans, session logs or secrets. After timeout/uncertain create, query matching remote PR state before retrying. Reconcile partial failures at their exact recovery point: a pushed branch stays pushed if PR creation fails, with no rollback claim. Verify the resulting PR's actual URL/state/head/base before reporting success.
9. **Report, then return.** Report actual commit/push/PR state, actual PR URL, checks and material limitations, alongside the summary/cleanup/journal/formatting outcome above. No CI polling, merge, local-main update or branch/worktree deletion; CI and GitHub merge remain the user's. After confirmed publication, call `workflow_exit` once with `publicationUrl` set to that verified HTTPS PR URL and end the turn. This argument carries display context only, not proof/authority or a publication operation. If exit fails/cancels, preserve the URL and task recovery paths, report actual cwd and wait for chat. Explicit exit without publishing remains available at every boundary by asking in chat for workflow_exit with no arguments, and never starts/resumes publication.

## Local merge — no push

- Resolve the local base branch in the recorded sourceRoot/originalCwd checkout using `git branch --show-current`; do not use gh metadata, remote defaults or guessed main. Task metadata records the starting commit, not the original branch name: inspect local history and confirm the target in chat if the source branch changed, is detached, does not contain the recorded starting commit, or is otherwise ambiguous. Never switch a dirty checkout to another branch. Verify its canonical root/common Git directory against the task association, ensure it is not the task branch, and inspect its status, index and any in-progress Git operation. Require a clean source checkout and no merge/rebase/cherry-pick/revert in progress in either checkout; preserve unrelated work and pause for direction otherwise.
- After the shared signed-commit/recovery steps, verify exact task branch/HEAD and contents again. Require no staged/unstaged tracked changes or non-ignored untracked files before choosing automatic cleanup; these still block removal. All ignored task files, including modified environment copies, dependencies, caches and local databases, are explicitly disposable on this route without per-file confirmation; source originals stay untouched. Do not delete files yourself to make it clean. If tracked/non-ignored pending work exists, pause for direction; explicitly keeping the worktree means use bare workflow_exit after a verified merge, not mergedInto.
- In sourceRoot run `git merge --ff-only -- <task branch>` first. If histories diverged, explain and ask before a non-fast-forward signed merge using `git merge --no-ff -S -m <merge subject> -- <task branch>` with the same configured identity/hooks and GPG recovery rules. No automatic rebase, squash, unsigned merge, reset or conflict resolution. On failure/timeout inspect actual source HEAD, status and merge state before retry; conflicts stay for user direction, never claim rollback or remove the worktree.
- Verify the exact task HEAD is an ancestor of source HEAD with `git merge-base --is-ancestor <task HEAD> HEAD` in sourceRoot, the selected base is still checked out, and the source status is clean with no in-progress merge. Inspect any merge commit's signature and hook effects. Missing/invalid signatures, unexpected contents or remaining task changes pause completion. Do not push either branch, fetch/pull, call gh, poll CI or delete the task branch.
- Report actual local base/task branch and commit/merge state, summary/cleanup/journal/formatting outcomes, actual checks and limitations, explicitly stating "nothing pushed; push remains manual." Then call workflow_exit once with mergedInto set to the verified local base branch (no publicationUrl) and end the turn. It revalidates local ancestry and absence of tracked/non-ignored pending task work, returns to the original cwd, then revalidates and runs helper-owned `git clean -fdX` only in the exact validated task root, checks for pending/ignored leftovers, then uses non-forced `git worktree remove -- <task root>`; the branch, source originals, sessions and external artifacts remain. No extra force flag for protected nested repositories. Never remove the active task worktree yourself before return. Failed/cancelled return preserves the worktree and ignored files; failed destination validation deletes nothing. Cleanup failure after return reports retained resources and possible partial ignored-file deletion, never uses --force or claims deletion succeeded. If retaining the worktree was explicitly chosen, report that and call workflow_exit without arguments instead.
