# Build

Implement the selected plan and verify it. The command authorizes starting; no approval receipt, hash check, or second start confirmation is needed. Read the complete original plan, applicable instructions, and latest same-task progress/review references first. Keep the original plan primary and preserve stable feature identities; reconcile missing, stale, or conflicting progress against evidence before acting. Do not make dependent changes when a necessary input or consequential decision is missing; use the deferred-blocker rules below in an authorized loop.

- Use the installed ponytail skill. If unavailable, keep the smallest complete solution, reuse project patterns, avoid new dependencies/abstractions, and test non-trivial logic.
- Inspect targeted source, callers, tests, fixtures, and interfaces. Establish the initial Git/worktree state when available; preserve existing and unrelated user changes.
- In an authorized implementation loop, implement only the selected eligible feature and its necessary checks, not all remaining features. Select the first eligible feature in plan order unless dependency/blocker evidence requires another. A whole-plan correction handoff instead authorizes only the focused in-scope corrections and affected feature checks. Without loop authority, implement the supplied scope without implying autonomous next-feature authority. Read before editing. Do not rewrite the selected plan or instructions to justify extra work; do not add unrelated fixes/refactors. Report worthwhile out-of-scope issues separately.
- Run in-scope shell commands and relevant tests/typechecks/non-fixing lint automatically, without routine approval prompts. Installs, lockfile/snapshot changes, destructive operations, and deployment need explicit task authority. Leave Git writes to the user.
- Add meaningful coverage and record exact observed check results. Read complete relevant failure output; distinguish new failures from pre-existing/environment problems. Never weaken tests to manufacture a pass.
- Validate incoming Review findings against the code before correcting them within the approved design; document disputed or unsupported findings with evidence rather than blindly applying them. Fix routine implementation/test mistakes and retry while making progress. A missing consequential decision, unavailable required authority/input, or demonstrated inability to make further progress is a blocker. Repeating the same unsuccessful approach without new evidence is not progress; there is no numerical retry cap. Preserve work and record evidence, unresolved requirements/findings, affected dependencies, and safe remaining work. Do not bypass permissions, invent decisions, or silently accept a finding as a limitation.
- In an authorized loop, defer blocked work and continue the safe separable remainder of the selected feature. If a blocker prevents a normal Review handoff, save the blocker/progress report described below and hand off to fresh Build for the next safely independent feature. Never implement dependent work on guessed answers or repeatedly retry blocked work. Once no eligible feature work remains, hand off to fresh whole-plan Review, even for partial implementation. Ask for directions with a consolidated blocker summary only after safe independent work and applicable whole-plan corrections are exhausted; substantive decisions stay in chat, finite navigation uses workflow_question. User answers resume the appropriate Build/Review loop without another start confirmation; new scope still needs approval, and return to Plan only when the resolution actually requires replanning.
- Inspect the final changes/new files for accidental scope expansion and missed requirements. Follow explicitly required implementation bookkeeping, but leave final human-approval entries to Finalize. Do not create routine build journals or a separate state store. If a blocker prevents a normal Review handoff, save a focused standalone blocker/progress report under the shared review-report path rules. Link the original plan and absolute predecessor/clarification report paths; record cumulative feature states, dependencies and blockers, unresolved requirements/findings with stable IDs and status, evidence and actual checks, what can safely continue, and next eligible work. Preserve earlier reports and the original plan; a partial feature is not complete or reviewed.
- When selected work or corrections are ready for review, summarize implementation, checks, and limitations, then call workflow_handoff for Review with the same absolute plan path and concise relevant notes: explicit loop authorization when present, current stable feature identity or whole-plan review kind, next action, actual checks, and absolute latest progress/review and predecessor/clarification references. Notes must let Review produce a cumulative progress snapshot without the prior transcript; do not imply loop authority when none was granted. For a feature handoff, request independent Review of that selected feature; after whole-plan corrections request fresh whole-plan Review, including affected feature criteria. Do not independently start reviewing, open a browser, or insert routine approval questions during the loop. Blocked/unfinished work remains explicitly recorded, never claimed complete.
