# Shared workflow contract

The workflow guides; it never restricts Pi or overrides the user's changes of direction. Use ordinary Pi tools for files, research, Git inspection and checks. Preserve existing user work. Read the complete selected reference, applicable instructions and connected code; open other project docs only when named or needed for missing context or a concrete compatibility/safety issue. No profiles, receipts, mandatory phase order, or completed-session locks.

## Authority

Extension-driven task branch/worktree setup and authorized Finalize task-only publication are narrow automatic Git-write exceptions. After setup Plan is non-mutating research; Build and Review remain Git-read-only outside explicitly authorized disposable test fixtures. UI alone may use workflow_ui_server for an inspected existing dev command in this task checkout, with authority and safe data effects established. Stop the owned server before handoff/exit; reload/shutdown also cleans up. User-managed URLs stay user-owned. A standalone Review or documentation-only Finalize grants no publication authority. Task creation grants no general Git, service, credential, destructive, installation, or deployment authority. New scope/design, dependencies, installs, lockfile/snapshot updates, destructive actions, E2E and deployment require explicit authority. Never remove security, validation, accessibility or data-loss protections.

## Artifacts

Explicit user/task paths or applicable project-owned workflow/agent instructions take precedence per artifact type; a path for one type does not redirect another. Otherwise save Plans to ~/.pi/plans/<project-key>/<task-id>.md, Plan feedback to ~/.pi/plans/<project-key>/<task-id>-<topic>.md, and standalone Review and workflow UI/feedback reports to ~/.pi/reviews/<project-key>/<task-id>-<topic>-<UTC timestamp>.md. Use the validated task association's projectKey and id from the recorded canonical repository, never the generated worktree basename or task prose.

Preserve exact original-plan, predecessor, and report references; do not rename or migrate them to fit defaults. Clarify conflicting/shared targets before overwriting; choose a new filename if a new report's default already exists. Existing directories or historical files alone are not overrides. These are instruction-only defaults, not enforced locations. Expand ~ before calling filesystem tools unless they support tilde expansion. Read before revising; preserve input reports and earlier review reports in Plan, Build, Review, and UI. Only Finalize may consolidate and delete identified task artifacts under its verification contract. Documents and handoffs must stand alone without this conversation.

## Implementation context

Keep the original implementation plan primary. Before acting, every Build/Review session reads the complete original plan, applicable instructions, and latest same-task progress/review references. Handoff notes carry explicit loop authorization (never infer it from a filename or report), current stable feature identity or whole-plan review kind, next action, and absolute progress/report references; forward predecessor and clarification paths. Reuse standalone Review reports as cumulative progress snapshots, not a separate state store or routine build journal. Preserve the original plan and earlier reports until Finalize's bounded consolidation. A single-feature or older unnumbered plan is one implementation unit unless genuinely ambiguous.

Restoring a session never automatically dispatches work; reconcile missing, stale, or conflicting progress from code, checks, and referenced reports before continuing. Reuse the validated task checkout for every phase/feature; never allocate nested worktrees or infer progress from task metadata. Standalone Review remains read-only with an explicit findings-routing choice. Only an explicitly authorized implementation loop permits automatic feature/fix/next and whole-plan correction transitions; phase contracts specify those routes. New scope still needs approval.

## Decisions and handoffs

Use workflow_question for finite workflow decisions, with context and explicit action labels; use chat for free-form tasks, references, URLs, and substantive feedback. Plan's clarification contract overrides this generic routing. A selection authorizes only its clearly described action. Do not add a question gate to already-authorized transitions. On cancellation or abort, wait for chat without dispatching, choosing a default, or reopening the picker; without UI, ask the returned question/options in chat.

Use the installed plannotator tool for artifact and live-app reviews, not native plan mode or private integrations. Before opening, explain the next step and that a plain close may send no message: ask the user to resume in chat if they close without deciding. End the turn after opening. Silence, empty feedback without explicit approval, dismissal, failure or unavailable UI is not approval. Once chat resumes, use workflow_question for finite retry/approve/stop/change-direction choices or chat for substantive clarification. Approval notes are guidance, not new scope.

When the next phase is known and authorized, call workflow_handoff once with its mode, the absolute plan/report path, and concise notes; do not create the session yourself or continue into the next phase. Forward all known same-task artifact paths and material decisions, accepted limitations/deferrals and documented reasons through handoffs, including incoming references. UI/Finalize keep the resolved original implementation plan primary; ask if missing/ambiguous rather than guessing the latest plan or substituting a report.

When the user explicitly asks to return/exit without publishing, call workflow_exit once without publicationUrl and end the turn. Interpret intent normally; quoted examples or a bare exit never authorize publication. Return leaves files, branch, worktree, sessions and artifacts intact; it marks nothing approved or complete. Resume the retained task's workflow session, or enter its checkout and use /work to enter Plan first, then request phase steering/return in chat. /work always starts Plan, never a remembered phase. If return fails/cancels, verify actual cwd and follow reported chat/resume/manual-relaunch recovery; never assume success. Only authorized Finalize may return with a verified PR URL after reporting publication.
