# Shared workflow contract

The workflow guides; it never restricts Pi or overrides the user's changes of direction. Use ordinary Pi tools for files, research and checks; inspect Git only for managed Git tasks. Preserve existing user work. Read the complete selected reference, applicable instructions and connected code; open other project docs only when named or needed for missing context or a concrete compatibility/safety issue. No profiles, receipts, mandatory phase order, or completed-session locks.

## Authority

All phase, routing, scope and procedural restrictions below and in the selected phase are defaults when no specific contrary user direction exists. At an unexpected blocker, follow the user's specific instruction within its stated scope in any phase; do not veto it by phase name, force a phase detour, or reconfirm an already clear instruction. Normal approvals, independent read-only Review and automatic routing remain unchanged otherwise. An exception does not imply unrelated new scope or blanket future permission, and outside /work these defaults add no gates to ordinary requests.

Explicit direction overrides workflow procedure, not higher-priority policies, missing capabilities, actual command failures, or security and data-loss protections. Preserve unrelated work; concrete destructive consequences need specific authority. Keep helper identity, containment and outcome checks intact. If a helper cannot handle an authorized deviation, explain its concrete limitation and use ordinary tools where appropriate; do not add generic bypass controls or describe a technical failure as a workflow prohibition. Forward the exact applicable exception and scope in existing handoff notes so a fresh session does not reinstate the blocker; no new persistent authority metadata.

Outside Git, work directly in the validated canonical directory: no repository/worktree creation, Git status/diff/publication, signing or authentication requests. In-place files and symlink destinations have no isolation, baseline or implicit rollback. Plan remains non-mutating; Review remains read-only. UI may use the inspected owned-server helper inside this root. A repository appearing later pauses the task, never grants publication authority. Successful non-Git Finalize consolidates/checks documentation, reports outcomes and automatically calls workflow_exit without publicationUrl; incomplete/failed completion stays for recovery. Explicit exit remains available.

Extension-driven task branch/worktree setup and authorized Finalize task-only publication are narrow automatic Git-write exceptions for managed Git tasks. After setup Plan is non-mutating research; Build and Review remain Git-read-only outside explicitly authorized disposable test fixtures. UI alone may use workflow_ui_server for an inspected existing dev command in this task checkout, with authority and safe data effects established. Stop the owned server before handoff/exit; reload/shutdown also cleans up. User-managed URLs stay user-owned. A standalone Review or documentation-only Finalize grants no publication authority. Authorized Finalize asks for local in-place merge (no push) or GitHub PR unless already explicitly chosen. The local choice permits only the verified source-checkout merge and helper-owned ignored-file disposal and non-forced merged-task worktree removal after successful return, retaining its branch; no remote/authentication work or push. Task creation grants no general Git, service, credential, destructive, installation, or deployment authority. Apart from the narrow managed-worktree preparation and local-cleanup exceptions below, new scope/design, dependencies, installs, lockfile/snapshot updates, destructive actions, E2E and deployment require explicit authority. Never remove security, validation, accessibility or data-loss protections.

## Managed-worktree preparation — Build/UI only

In managed Git tasks only, automatically prepare missing prerequisites just before the first Build check or UI startup that needs them, using ordinary agent tools without routine install/copy confirmation or a detour from UI to Build. Initial Plan entry still copies committed files only; Plan remains non-mutating and Review read-only. Non-Git tasks receive no new preparation authority. Inspect project instructions, manifests, lockfiles and invoked scripts (including normal install lifecycle hooks), then use the project's existing install command at the appropriate task app/workspace root. Reuse usable dependencies; repeat only for missing or changed prerequisites, not every handoff. No new runner, tool, dependencies, intentional manifest/lockfile updates or dependency-directory sharing/symlinking.

Copy only identified required Git-ignored app files (not just environment files) from recorded sourceRoot to the corresponding relative task path, only when the destination is missing. Verify each source/destination is untracked and ignored in its checkout and contained within its canonical root, including existing parent paths; never follow symlink escapes, overwrite task files or modify source originals. Traverse directories only as needed for identified files, never copy ignored trees, dependencies, caches or databases wholesale. Copy credential-bearing files without reading their contents into model-facing results, logs or artifacts; suppress raw installer/app output that could disclose secrets and report only sanitized diagnostics. Do not inject credentials into commands/environment. Worktrees are not a sandbox: inspected hooks and copied configuration can access real services. Unknown commands, missing required source files, incompatible existing configuration, required lockfile changes, migrations, external-service provisioning or unclear data effects are concrete blockers: explain and ask rather than guess or bypass protections. Unrelated installs, feature edits in UI, infrastructure, deployment and Git writes remain unauthorized.

## Artifacts

Explicit user/task paths or applicable project-owned workflow/agent instructions take precedence per artifact type; a path for one type does not redirect another. Otherwise save Plans to ~/.pi/plans/<project-key>/<task-id>.md, Plan feedback to ~/.pi/plans/<project-key>/<task-id>-<topic>.md, and standalone Review and workflow UI/feedback reports to ~/.pi/reviews/<project-key>/<task-id>-<topic>-<UTC timestamp>.md. Use the validated task association's projectKey and id from the recorded canonical repository (or canonical non-Git root), never the generated worktree basename or task prose.

Preserve exact original-plan, predecessor, and report references; do not rename or migrate them to fit defaults. Clarify conflicting/shared targets before overwriting; choose a new filename if a new report's default already exists. Existing directories or historical files alone are not overrides. These are instruction-only defaults, not enforced locations. Expand ~ before calling filesystem tools unless they support tilde expansion. Read before revising; preserve input reports and earlier review reports in Plan, Build, Review, and UI. Only Finalize may consolidate and delete identified task artifacts under its verification contract. Documents and handoffs must stand alone without this conversation.

## Implementation context

Keep the original implementation plan primary. Before acting, every Build/Review session reads the complete original plan, applicable instructions, and latest same-task progress/review references. Handoff notes carry explicit loop authorization (never infer it from a filename or report), current stable feature identity or whole-plan review kind, next action, and absolute progress/report references; forward predecessor and clarification paths. Reuse standalone Review reports as cumulative progress snapshots, not a separate state store or routine build journal. Preserve the original plan and earlier reports until Finalize's bounded consolidation. A single-feature or older unnumbered plan is one implementation unit unless genuinely ambiguous.

Restoring a session never automatically dispatches work; reconcile missing, stale, or conflicting progress from code, checks, and referenced reports before continuing. Reuse the validated task root for every phase/feature; never allocate nested worktrees or infer progress from task metadata. Standalone Review remains read-only with an explicit findings-routing choice. Only an explicitly authorized implementation loop permits automatic feature/fix/next and whole-plan correction transitions; phase contracts specify those routes. New scope still needs approval.

## Decisions and handoffs

Use workflow_question for finite workflow decisions, with context and explicit action labels; use chat for free-form tasks, references, URLs, and substantive feedback. Plan's clarification contract overrides this generic routing. A selection authorizes only its clearly described action. Do not add a question gate to already-authorized transitions. On cancellation or abort, wait for chat without dispatching, choosing a default, or reopening the picker; without UI, ask the returned question/options in chat.

Outside Git, clean standalone/whole-plan Review offers exactly: Approve code and go to UI; Approve code, skip UI, and go to Finalize. No browser file/code review outside Git; review explicitly scoped task files against plan/check evidence and disclose the missing baseline. Chat approval and optional live UI remain available.

Use the installed plannotator tool for permitted artifact and live-app reviews, not native plan mode or private integrations. Before opening, explain the next step and that a plain close may send no message: ask the user to resume in chat if they close without deciding. End the turn after opening. Silence, empty feedback without explicit approval, dismissal, failure or unavailable UI is not approval. Once chat resumes, use workflow_question for finite retry/approve/stop/change-direction choices or chat for substantive clarification. Approval notes are guidance, not new scope.

When the next phase is known and authorized, call workflow_handoff once with its mode, the absolute plan/report path, and concise notes; do not create the session yourself or continue into the next phase. Forward all known same-task artifact paths and material decisions, accepted limitations/deferrals and documented reasons through handoffs, including incoming references. UI/Finalize keep the resolved original implementation plan primary; ask if missing/ambiguous rather than guessing the latest plan or substituting a report.

When the user explicitly asks to return/exit without publishing, call workflow_exit once without publicationUrl and end the turn. Interpret intent normally; quoted examples or a bare exit never authorize publication. Return leaves files, branch, worktree, sessions and artifacts intact; it marks nothing approved or complete. Outside Git, resume the retained workflow session to continue its identity; a new unrelated session creates a new task, never rediscovers one from files. For Git, resume the retained task's workflow session, or enter its checkout and use /work to enter Plan first, then request phase steering/return in chat. /work always starts Plan, never a remembered phase. If return fails/cancels, verify actual cwd and follow reported chat/resume/manual-relaunch recovery; never assume success. Only authorized Finalize may return with a verified PR URL after reporting publication, or mergedInto after reporting a verified local merge. The latter revalidates ancestry and absence of tracked/non-ignored pending task work, returns first, then revalidates and discards all ignored task files with helper-owned git clean -fdX before checking for leftovers and removing the task worktree without force; it keeps the branch and never pushes. This explicitly permits deletion of modified environment copies, dependencies, caches and local databases, not source originals. Failed/cancelled return or destination validation deletes no ignored files; cleanup failures after return may leave partial cleanup and must report retained resources. Protected nested repositories are never force-cleaned. Bare exit and PR return never remove worktrees.
