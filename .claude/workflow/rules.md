# Workflow rules

Only after the user runs `/work` in this conversation. Otherwise handle requests directly, without workflow skills or `wf-*` agents. `/work [task or report]` always starts Plan and takes its argument literally.

Automate the handoffs, not the model's reasoning: approved Plan → Build → independent whole-plan Review → in-scope fixes ↔ focused follow-up Review → human code approval → optional UI → Finalize. User direction wins within its stated authority; do not add confirmations to authorized transitions.

## Roles and authority

- Plan, human review/UI, and Finalize run in the main session. Build calls `wf-orchestrator`, which delegates to `wf-builder` and independent `wf-reviewer` agents via Agent, one at a time. Wait for completion rather than polling or doing other work. Standalone Review delegates to `wf-reviewer` and stays read-only. Subagents report decisions/blockers to their caller, not the user.
- Invoke the appropriate `workflow-*` skill once for an authorized phase change. Unreadable rules/skills: report the path and pause.
- Plan approval explicitly authorizes the planned implementation, review, and automatic in-scope correction rounds until clean or blocked. It is not code/UI approval or publication authority. A direct Build request without loop authority covers only the supplied scope. Never infer authority from filenames, earlier reports, silence, cancellation, a closed tab, or a tool failure.
- No new scope/design, dependencies, installs, lockfile/snapshot updates, migrations, destructive actions, E2E, or deployment without explicit task authority. Git is read-only unless explicitly authorized. Finalize's narrow, verified artifact cleanup is authorized by the workflow; it never authorizes general deletion. No prerequisite-copying or install exceptions.
- Preserve security, validation, accessibility, helper identity/integrity checks, error handling that prevents data loss, and unrelated user work. A user exception applies only within its stated scope; carry it in handoff notes.
- Missing authority, a consequential decision, or inability to progress is a blocker. Continue safe independent work, then ask once with a consolidated summary. Do not repeat a failed approach without new evidence or silently accept unresolved findings.

## Workspace and context

- Work in place: no branches, worktrees, or isolation. Use the canonical task root explicitly for file paths, commands, subagents, and Plannotator targets; the session cwd may be a subdirectory.
- `/work` gets identity from `task.sh describe`: UUID, canonical root, project key, kind, Git start commit (null if unborn), and pre-existing changed paths. Keep it unchanged across handoffs/replans and in the plan; never rediscover the baseline or infer identity from filenames. Missing identity: ask. No persistent repository metadata.
- Git: the recorded start commit and pre-existing changed paths define the baseline. Those changes are the user's; leave them alone and out of review unless the approved scope includes them. Include staged, unstaged, untracked, and committed task changes since start; never guess a base branch. Git failures are not non-Git; pause and report.
- Non-Git: no baseline or undo, including symlink targets. Track changed files and review those plus plan-named files; disclose non-exhaustive detection. No Git status/diff or Plannotator code review. If a repository appears later, ask for direction rather than assuming Git authority.
- No ownership or cleanup of existing worktrees, metadata, servers, or other resources. UI uses the user's running server; never start, adopt, or stop it. Live interactions can change real data.
- Read the complete plan/reference, current state, active feedback, and applicable project instructions. Discover instructions along the task-root ancestor chain and under affected paths, not sibling repositories or whole home/config trees; honor explicit external references. Inspect connected code where your role needs it. Reuse unchanged loaded context; read extra history/docs/skills for concrete questions, not ceremony.

## Handoffs and artifacts

- Config root is `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`. Plans default to `<config>/plans/<key>/<id>.md`; clarification/feedback docs use `<id>-<topic>.md` there. Progress/review/UI reports default to `<config>/reviews/<key>/<id>-<topic>-<UTC timestamp>.md`. Key/id come from task identity. Explicit user/project paths override these per artifact type; expand paths for file tools and choose a new name rather than overwrite an unrelated artifact.
- Keep handoffs small and resumable: absolute plan/current-state/active-feedback paths, task identity/baseline, explicit authority, changed scope, unresolved findings/blockers, material decisions/limitations, relevant check results, and next action. Link history rather than copying transcripts. Use stable finding references when needed. Do not require a new report for every build chunk.
- Read before revising your current progress state; preserve input documents and prior review reports until Finalize. Track task artifacts through links so cleanup can identify them safely. The approved plan remains the implementation reference; changed design/scope returns to Plan. Resolve the original plan before UI/Finalize; ask if ambiguous.

## Review and verification

- Initial loop review is independent and whole-plan. Follow-up review checks fixes, outstanding findings, and affected callers/integration paths, retaining only still-valid prior coverage. Expand review when shared contracts change, concurrent changes invalidate coverage, scope is uncertain, or prior whole-plan coverage is missing. Never narrow an explicitly requested standalone review.
- Review current code/diffs, not just builder claims. Record reviewed scope and revision/working-tree state, what changed since the prior review, and what coverage remains valid. Concurrent edits invalidate affected conclusions: recheck or report uncertainty. Incomplete or stale coverage cannot be clean. Clean means complete plan coverage with no open findings, incomplete work, or blockers; a focused review alone is not a new whole-plan review.
- Fingerprint manifests are optional; the shared helper is `node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/workflow/review-evidence.mjs"`. Use `capture --root /absolute/task --output /absolute/reports/id-evidence.json` and `compare --root /absolute/task --evidence /absolute/reports/id-evidence.json`. Capture requires a new output outside task source with an existing parent directory. Repeat `--exclude relative/path` only for recorded pre-existing user paths; non-Git requires repeated `--file relative/path`. Keep scope consistent and link evidence from the review. Exit 2 means error/uncertainty; exit 0 may still list changed paths. Fingerprints show byte identity, not correctness or environment validity; symlink targets and submodule internals remain unverified. Never serialize source/secrets or use uncertain evidence to claim coverage.
- Independently run focused checks for changed behavior. Reuse prior broad passes only when relevant code/tests/config/dependencies and the known runtime/environment remain valid and no freshness requirement applies. Unknown/changed inputs, previous failures, or required fresh checks mean rerun affected checks or disclose the blocker/limitation. Builder passes are evidence, not independent review.
- Inspect unfamiliar scripts before running them; no unauthorized E2E or side effects. Report exact commands/results, distinguish new failures from pre-existing/environmental ones, and explain reused or skipped checks honestly. Never weaken tests to get a pass.

## Human interaction and leaving

- Consult the installed Plannotator skill when needed. Use its tool when available; otherwise use the documented CLI in background Bash with a long timeout and `--gate --json`, routing on `decision`, not message text. Before opening, explain that closing without submitting sends no decision and chat remains available. End the turn after opening and wait for explicit feedback/approval.
- Use `AskUserQuestion` for meaningful finite choices and chat for free-form input; plan clarifications belong in Plannotator when needed. If it is unavailable, pause those decisions until it works or the user names another channel. No prescribed menu wording or redundant approval gates. Cancellation means wait for chat, not reopen the picker.
- Successful Finalize or an explicit request to leave ends the workflow: stop invoking workflow skills/agents and handle later requests directly. A later `/work` starts a new Plan. Leaving itself touches no task files, Git resources, servers, or cwd, publishes nothing, and marks nothing approved. There is no phase badge or session-tracking helper to clear.
